# Project agent notes

- Azure App Service deploys here are cross-stack: `frontend/vite.config.js`, `backend/config/settings.py` (`TEMPLATES`, `STATICFILES_DIRS`, `STATIC_URL`), `backend/config/urls.py`, and Azure workflows must stay aligned or the deploy can go green while the SPA serves broken assets/routes.
- If PostgreSQL stays private behind a VNet/private endpoint, switching between `SWA + App Service` and same-origin does not remove the backend's VNet requirement; only the frontend entrypoint changes, and App Service VNet Integration still needs a separate subnet and a paid tier.
- Treat `azure-same-origin` as a deploy variant derived from `azure`, not as a second product branch; land shared/product changes in `azure` first, then sync them forward.
- The intended branch-specific drift for `azure-same-origin` is concentrated in routing/deploy files (`backend/config/settings.py`, `backend/config/urls.py`, `frontend/src/App.tsx`, `frontend/vite.config.js`, and sometimes workflow/static-hosting config); wider diffs usually mean the branch was allowed to drift.
- App Service env var changes don't reload the running Django process; a manual `Restart` from the portal is required for new `CSRF_COOKIE_SAMESITE`, `CORS_ALLOWED_ORIGINS`, etc. to take effect.
- App Service outbound connections to PostgreSQL pick a random IP from the deployment-unit pool at runtime, so the PostgreSQL firewall must allow ALL outbound IPs listed in the App Service Properties (both `Outbound IP addresses` and `Additional outbound IP addresses`). Allowing just one will cause intermittent failures.
- PostgreSQL Flexible Server's "Allow public access from any Azure service within Azure" checkbox is NOT scoped to your subscription; it opens to all Azure tenants. Use IP-range firewall rules or Private Endpoint instead.
- App Service cold start on paid tiers can reach 30–90 seconds. Set curl/health-check timeouts to ≥90s and avoid relying on Azure's default 30s load-balancer probe for startup validation.
- The same-origin build config lives in `deploy.yml` (`VITE_API_URL=/api`, `VITE_STATIC_BASE=/api/static/`). The split-origin build config lives in the SWA workflow (`VITE_API_URL=https://...azurewebsites.net/api`). Switching between modes only requires env vars + choosing which workflow trigger is active, not code changes.
